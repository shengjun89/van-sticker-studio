多 Agent 开发与 AI 代码质量：
从 vibe coding 到 agentic engineering

先说结论：Karpathy 本人从未把 vibe coding 推荐为产品开发方法。他把 vibe coding 明确限定在「一次性周末项目」，特征就是不读 diff、不理解代码。他 2025 年 6 月的《Software 3.0》演讲和之后被转述的「agentic engineering」转向，恰恰是把重心从「让模型写」移回人定规格、管上下文、做验证。这页把一手资料、独立开发者的真实多 agent 案例、以及一套可直接套用的质量闭环整理在一起。

CORE THESIS · 一句话工作法

把人从「写代码者」升级为规格作者 + 验收官，把 agent 降级为在沙箱 / 分支里、按验收标准干活、产出必须被机器复核的工人。

小规格 → 小任务 → 一分支一 agent → 机器门禁先行（类型 / lint / 测试 / 构建 / 哈希）→ 换一个 agent 做评审 → 人亲自跑关键路径 → 小 PR 合并 → 预览部署验证

置信度说明：Karpathy 2017 / 2025 年一手论述、Willison 2025 年两篇文章、GitHub Spec Kit 仓库原文为高置信；2026 年 Sequoia「agentic engineering」引言、各类「提速倍数」、SWE-bench 最新分数多为二手转述或当事人自述，文中已逐处标注降级，引用时请带上标注。

01

Karpathy 的路线：从 Software 2.0 到 agentic engineering

四站连起来看，他的立场其实从没变过：能跑 ≠ 可解释、可审计；越是让机器生成，越要把规格和验证握在人手里。

2017-11

Software 2.0 一手原文

Software 1.0 是人写的显式指令；2.0 的「代码」是神经网络权重，没人直接写——源代码变成「数据集 + 网络架构」，训练就是编译，开发工作变成整理、清洗、标注数据；出问题时不是改代码行，而是补失败案例的数据。

对今天最要紧的警示：2.0 会「silently fail」（静默失败——悄悄学到训练数据的偏见也不报错），且常面临「90% 准确但可理解 vs 99% 准确但不可理解」的取舍。这正是 agent 代码的原型问题。

出处：Andrej Karpathy, “Software 2.0”, Medium, 2017-11-11 · karpathy.medium.com

2025-02

Vibe coding 原始表述 一手原推 · Willison 全文引用

「完全沉浸在氛围里，忘掉代码的存在……我总是点 Accept All，不再读 diff；报错就整段复制粘贴回去，通常就修好了。」 “I ‘Accept All’ always, I don't read the diffs anymore… It's not too bad for throwaway weekend projects.”

注意限定词：throwaway weekend projects（一次性周末项目）。工具背景是 Cursor Composer + Sonnet、语音输入，几乎不碰键盘。日期有个出入：Willison 引用时写 2 月 6 日，多数二手资料写 2 月 2 日，研究未直接打开 X 原帖核实，稳妥写法是「2025 年 2 月初」。

Willison 的收窄定义（2025-03-19）：vibe coding 应特指「用 LLM 写代码而不评审它写的代码」；凡是评审过、测试过、能向他人解释清楚的代码，哪怕全是 LLM 写的，也不是 vibe coding，而是软件开发。

出处：Simon Willison, “Not all AI-assisted programming is vibe coding”, 2025-03-19 · simonwillison.net

2025-06

Software 3.0 与「agent 的十年」 演讲一手 · 逐字稿二手

YC AI Startup School 演讲《Software Is Changing (Again)》（2025-06-18）：1.0 = 代码，2.0 = 权重，3.0 = 提示（自然语言）即程序，LLM 成为运行时——LLM ≈ CPU、上下文窗口 ≈ 内存、API ≈ 系统调用。

对「演示级」的直接批判：不要只做炫目的全自主 agent 演示；要做 partial autonomy（部分自主）产品，配 autonomy slider（自主程度滑杆）和定制 GUI，让「生成—验证」循环极快，但人始终在回路。时间判断也不是「2025 是 agent 之年」，而是「2025–2035 是 agent 的十年」——他以自动驾驶为例：完美 demo 之后仍需多年的人在回路打磨。

两个认知缺陷：jagged intelligence（某些任务极强、基础逻辑上离奇出错）与上下文窗口外即遗忘。直接推论：规格、验收、外部记忆不能只放在对话里，必须落成文件和仓库。他还提醒：vibe 一个简单 app 时「写代码是最容易的部分」，难的是 auth、环境变量、部署、域名、支付这些环节。

出处：YC 演讲视频为一手；逐字稿 youtubetotranscript.com、全文转载 singjupost.com 均为二手

2026

Agentic engineering 二手转述 · 无官方逐字稿

据多篇二手文章转述，Karpathy 在 Sequoia AI Ascent 2026 上提出：“Vibe coding raised the floor. Agentic engineering raises the ceiling.”（vibe 抬高了下限；agentic 是在保持专业质量、安全、架构标准的前提下提速。）据称他自述 2025 年 12 月前后发生翻转：手写代码比例从约 80% 降到约 20%，99% 的时间不再直接写代码，而是指挥 agent——但「engineering」意味着标准仍要守。

「你可以外包思考，不能外包理解。」 “You can outsource your thinking, but you can't outsource your understanding.”（据二手转述，未见一手逐字稿）

据转述，他的方法是：先与 agent 共同打磨非常详细的 spec（基本就是一份文档），再让 agent 写；人保留审美、判断与 oversight。研究判断：即使把 2026 年的引言全部降级为转述，其方向与 2017、2025 年的一手论述一致——从「忘掉代码」退回「规格 + 验证 + 理解」。

出处（二手）：Agentic Insights · elevatex.de · thedeepfeed.ai

附：Karpathy 用 LLM 的日常习惯 二手笔记

《How I Use LLMs》（2025-02-28 视频）的笔记要点，条条都能直接变成团队规则：保持会话短、换话题就开新会话（长上下文分散注意力且更贵）；用搜索、代码执行等工具对抗幻觉，不只依赖模型的参数记忆；最重要的指令与上下文要显式放进上下文窗口；先做简单版本跑通，再迭代到复杂版本。这正是后面「主 agent 保持干净上下文、子 agent 各自独立上下文」的理论来源。

出处（二手笔记）：jinyoung-park.dev · dilopa.com

02

Simon Willison：把 LLM 当「过度自信的结对助手」

Willison 是把 agentic engineering 写成可操作指南的人。他的两篇文章（一手，高置信）几乎可以直接当一人开发者的操作手册。

生产金律：「我不会提交任何我不能向别人准确解释其作用的代码。」 出自 “Not all AI-assisted programming is vibe coding”, 2025-03-19

两种模式，泾渭分明

探索期用 LLM 做选项调研与原型，先证明关键需求可行；生产期切换为「专制模式」：把 LLM 当实习生，按详细指令打字——他常直接给定函数签名让模型填函数体，再让模型按指定技术栈写测试。心智模型是：LLM 查资料快、出示例快、不厌其烦做枯燥活，但会犯「非人类式」错误（幻觉一个不存在的库或方法），所以要建立核查习惯，而不是用对人类同事的信任标准去对待它。

上下文管理：清零是 feature

新会话清零不是缺陷而是特性；对话跑偏时最有效的修复常常是清空重开。开局把现有代码整段贴入做种子上下文；给几个完整示例再要求仿写。选库策略对框架型项目尤其重要：优先选流行、稳定、训练数据里示例多的「boring technology」，只在项目真正的独特卖点上创新；新库或大版本 breaking change 必须在提示里喂真实示例，不能指望模型「知道」。底线一句：「如果你没有实际运行它，那它还不能算是一个可用的系统。」

Agentic Engineering Patterns：人的剩余工作

他的指南总纲给 coding agent 的定义是：能在循环里执行工具去达成目标——定义性能力是「能执行代码」。没有执行能力，LLM 输出价值有限；有了执行，agent 才能迭代到「可证明能跑」。人的剩余工作一点不少：定目标、给工具、定恰当的细节程度、验证并迭代到稳健可信。关键一句：LLM 不会从过去的错误中学习，但 coding agent 可以——前提是人主动把教训写进指令与 harness。这就是「每次踩坑都沉淀为一条门禁 / 检查清单」的依据。

成本实证（一手小样本）：他文中一个 Claude Code 示例 /cost 显示总成本 $0.61、API 用时 5 分 31 秒、墙钟 17 分 18 秒。说明小而明确的任务可以极便宜——但不能外推为所有任务都便宜。

安全边界：别让一个 agent 集齐三件套

Willison 长期讲提示注入与沙箱，可操作翻译只有一条：不要让同一个 agent 同时拥有「私密数据 + 不可信输入 + 对外发送能力」。无人值守的 agent 一律放进容器 / 虚拟机 / 操作系统沙箱；密钥不贴进提示词，给能力（短期凭证、代理工具）而不是原始密钥；所有 agent 分支过密钥扫描。可用的设计模式包括 dual LLM（特权 LLM 只做规划、隔离 LLM 只读不可信内容并返回符号变量）、plan-then-execute、上下文最小化等。

出处（一手）：Here's how I use LLMs to help me write code, 2025-03-11 · Agentic Engineering Patterns 总纲 · 提示注入设计模式整理, 2025-06-13

03

一人团队怎么分工：1 个主 agent + 4 个专员

来自一个 2026-10-22 的一手实操案例（OpenCode）：1 个主 agent 拥有实现，4 个子 agent 各管一摊；每个 agent 一个 Markdown 定义文件、可版本控制；每个子 agent 配一个专用 skill（检查清单与流程），按需加载以免污染上下文。点下面的页签看每个角色的边界。

由人指挥的总控：拆任务、定规格、收敛合并、拍板。它不直接大段写实现——避免主上下文被实现细节污染，保住全局判断力。

只干什么

把需求拆成可独立验收的小任务；维护任务清单与依赖顺序；汇总各专员产出，做合并决策。

不干什么

不亲自写大段实现代码；不替专员做评审；不跳过门禁强行合并。

产出物

任务清单、规格索引、合并决策记录。

关键规则

提议先行、两次确认：先给「改哪些文件、为什么」的提议，等人批准；执行时每个写操作再经一次确认；中途出现意外停下汇报，不擅自即兴发挥。

按规格在自己的分支 / worktree 里写代码与测试的工人。它是唯一默认有写权限的角色。

只干什么

严格按规格实现；同步写测试；每步跑门禁命令；完成后提交 PR 草稿和交接五件套。

不干什么

不审自己的代码；不改规格；不扩大范围；不拥有验收测试的最终决定权——改验收测试需人批准并留理由。

产出物

分支 + PR + 测试证据（命令原文、退出码、通过 / 失败数）。

关键规则

发现规格有问题就停下提问，标 [NEEDS CLARIFICATION]，绝不静默假设、绝不编造不存在的事实（品牌、文案、版本号只 flag 提问）。

Fresh eyes 评审者。案例作者的原话：刚写完代码的 agent 是最差的评审者——换一双眼睛本身就是质量手段。

只干什么

只看 diff：正确性、可读性、边界条件、安全性；输出结构化回执。

不干什么

不重写代码（只给意见，除非人批准）；不评审自己参与写的代码。

产出物

按严重度排序的评审报告：每条带 path:line、为什么重要、具体修法。

关键规则

只给读权限。评审只有人真的读了才有效——人是最后一道、也是唯一能拍板合并的人。

专职「证伪」：它的工作不是让测试变绿，而是证明实现真的对。

只干什么

写 / 跑测试；做失败注入（故意改坏实现，确认测试会变红）；跑关键路径手动验证并留截图。

不干什么

不为了绿而改测试断言；不接受「只绿不红」的测试——没在坏代码上红过的测试等于没有测试。

产出物

测试报告 + 失败复现步骤 + 关键路径验证证据。

关键规则

修 bug 时先加复现测试（红）再修（绿）；合并前跑全量门禁，不只跑改动文件的测试。

让项目「换个会话也不失忆」的角色：文档和资产是 agent 之间真正的交接载体。

只干什么

同步 README / changelog；核对二进制资产（如 GLB）清单与哈希；维护规格、ADR、任务清单等交接文件。

不干什么

不编造未验证的事实；不知道的标出来提问，而不是补一个 plausible 的值。

产出物

文档 diff、资产清单（文件名 + 哈希 + 大小预算）。

关键规则

子 agent 之间不直接共享上下文，共享文件系统上的产物：上一棒写文件、下一棒读文件，会话结束也不丢。

角色表出处：一人 + 四专员案例（一手，2026-10-22）dev.to / playfulprogramming；测试者 / 文档员的边界为本研究按同一原则补齐的建议配置。按需增设（不常驻）：架构员（只出接口与 ADR）、调试员（只诊断根因、不直接修，避免用「最近的 plausible 修复」掩盖真因）、安全员（只审密钥、权限、注入面）。代价要坦白：多 agent = 更多 token 与等待；一行业务修复用整套团队是过度设计，直接用主 agent。

另外两个真实案例，值得抄的点

Jeremy King：规格 → Issue → 云端 agent → 多轮评审 → CI/CD（一手自述）。先用 Claude + 自定义命令写详细规格，拆成 4–8 小时粒度的任务（过大则 agent 超时或出垃圾），转成 GitHub Issue（他称 GitHub 是「中枢神经系统」），指派云端 agent 常在夜间跑、出 PR，再由其他 agent 与本地 CLI agent 多轮评审，全套 CI/CD 把关：每次 push 构建、覆盖率、Playwright 端到端、staging / 生产门禁。他自述 PR 通常 80–90% 生产就绪、「10–20 倍 pace」——均为个人宣称、无独立测量，不作立项依据；可迁移的是机制本身：Issue 是天然的任务队列与交接载体，云端 agent 适合夜间批量、本地 agent 适合快速迭代。

Stuart Jeff 的演进（自述）：两年半从「聊天助手答疑」→「协作编辑文件」→「编排的 agent workforce」；瓶颈从「写」移到「审」，再移到「建造替你审的验证体系」。这句话可以当一人开发者的路线图：你最终的产出不是代码行数，而是验证体系。另一个 8 agent 协作 10 周的自述案例教训类似（agent 需要管理而非仅提示词，否则会交未测试代码、删半个代码库的 mega-PR），但其规模对一人项目过重，只取管理结论、不照搬规模。

出处：jking.ai · stuartjeff.com · 8 agent 案例（dev.to，自述，需降级）

并行隔离三层，缺一不可

层 1 · 分支（逻辑隔离）：每任务一分支，PR 是合并单位，主分支常绿是铁律。层 2 · worktree（文件隔离）：git worktree add ../proj-feature-a -b feature-a，每 agent 一个目录一个分支。但要写进团队须知：worktree 只隔离文件，不隔离端口、本地数据库和机器外写操作；同文件并行仍会冲突；每个 worktree 是全新 checkout，要重装依赖、配不同开发端口、处理 gitignored 的 .env（可用 .worktreeinclude 复制白名单文件，但绝不复制真实生产密钥）；冲突由人合并，不让 agent 自行「解决」后悄悄改语义。层 3 · 沙箱 / 容器（系统隔离）：无人值守、能联网或能读不可信内容的 agent 一律进容器 / VM，默认只读、低网络、低凭证。

出处（二手，多源一致）：Worktree 并行指南 · Worktree 指南 2。另有二手转述称「agent teams 约为标准会话 7 倍 token」——属厂商 / 社区说法，预算应以自己跑一周的账单实测为准。

任务拆分：按「可独立验收」切，不按文件切

一个任务 = 一份规格 + 一组验收标准 + 一个分支 + 一次可独立合并的 PR。动手前问 4 句：① 它不依赖另一个任务的未完成输出吗？（依赖就串行，不要并行）② 验收能否用一条命令 / 一次运行判定？（不能，就先把验收写出来再开工）③ 改动文件集合与其它并行任务基本不重叠吗？（重叠就合并任务或串行）④ 回滚是否只要 revert 这一个 PR？（不能，就再切小。）反模式：「做一个完整功能（含登录、注册、重置、OAuth、限流与全部测试）」式一句话大任务；「先做原型、以后再收拾」却不留规格与测试。

04

一人工作流模板：从需求到上线的闭环

点每个阶段看具体动作。这是把前面所有原则压成一条流水线的结果，可以直接照着执行。

阶段 0 · 立规矩（一次性，约半天）

执行：人
  • 写 constitution.md：技术栈、TypeScript strict、测试与 lint 门禁、PR 大小上限、密钥规则、资产预算、合并必须人批准。
  • 写 AGENTS.md：各 agent 的角色、工具权限、交接五件套格式、禁止事项（禁 --no-verify、禁擅自改验收测试、禁编造事实）。agent 定义文件入 git，与代码同版本。
  • 配 CI：typecheck + lint + test + build + 资产校验 全绿才是合并必需条件；配预览部署。本地一条命令 = CI 一条命令。

阶段 1 · 需求 → 规格

执行：人主导，agent 起草
  1. 人用一句话写清问题与用户价值。
  2. agent 起草一页规格：目标 / 非目标 / 验收场景（Given-When-Then 式）/ 边界与异常 / 回滚方式。
  3. 人审规格：逐条问「这条验收能否判定」；有 [NEEDS CLARIFICATION] 就先答问，不开工。
  4. 规格入 git（或写进 GitHub Issue），成为本任务的唯一真相来源——规格评审比代码评审便宜，且能拦截整批返工。

阶段 2 · 拆任务

执行：主 agent，人审计划
  • 拆成 4–8 小时粒度、可独立验收的任务；标注可并行项与文件排他集合。
  • 每任务一分支；并行时一任务一 worktree。
  • 人先审「切分计划」：拒绝「重构 + 新功能混装」，拒绝超大 PR 计划（参考上限约 100 行级，超了打回重切）。

阶段 3 · 实现

执行：实现者 agent（隔离环境）
  • 按规格实现 + 写测试；每步跑门禁；新行为走红绿循环（先红、再绿、再重构）。
  • 中途发现规格问题：停下提问，不擅自改规格、不即兴发挥。
  • 产出：分支 + PR 草稿 + 交接五件套（见下方模板）。

阶段 4 · 评审

执行：评审者 agent + 测试者 agent，人最后
  • 门禁顺序：机器先审，人后审。类型检查 → lint → 单元测试 → 构建 → 预览部署冒烟，任何一步红，PR 不进人的评审队列。
  • 评审者只看 diff，按严重度出报告；测试者做先证伪与关键路径手动验证。
  • 人读评审报告、亲自跑一遍关键路径、看预览部署截图。不合格回到阶段 3（同一分支），并把教训写进 AGENTS.md / 检查清单。

阶段 5 · 合并与上线

执行：人拍板
  • 小 PR 合并，单逻辑事、可独立 revert；人必须能解释每一行合并代码的作用（Willison 金律）。
  • 合并后主分支门禁再跑一次；预览部署验证通过才推生产。
  • 生产部署留回滚方案（前一版本 / 前一个 Worker 版本）。
  • 记一笔账：实际成本（/cost）、耗时、踩坑、门禁是否拦住过问题。

阶段 6 · 复盘与 harness 沉淀（每周约 30 分钟）

执行：人 + 文档员
  • 把本周真实 bug 转成自有验收 harness 的新题（隐藏测试）。
  • 把 agent 的系统性错误写成「禁止模式 + 正确示例」放进 agent 上下文。
  • 删掉已过时的规则——规则只增不减会变成噪音。
  • 节奏建议（本研究的建议，非来源事实）：并行路数不超过 3 路——并行超过评审能力就是负收益，瓶颈在人审，不在 agent 产出；每天留固定「评审时段」集中审 PR；夜间长任务只跑「失败即停、不自动合并」的任务；每会话结束记 /cost，每周复盘哪个任务 token 最高、为什么。

交接五件套：每一棒必须留下的东西

子 agent 之间不靠对话记忆交接，靠这份结构化回执。不知道的事实标 [NEEDS CLARIFICATION]，不编造。

HANDOFF TEMPLATE · 复制后贴进 PR / Issue 
## 交接回执
1. 改了什么：文件清单 + diff 摘要（不写"我优化了代码"这类空话）
2. 按什么规格：规格 / Issue 编号，验收条目逐条对应打勾
3. 跑了什么：命令原文 + 退出码 + 通过/失败数（禁止只写"测试通过"）
4. 没改什么 / 已知局限：明确边界与未覆盖项；不知道的标 [NEEDS CLARIFICATION]
5. 下一步：需要人拍板的问题清单（编号提问，等答复再继续）
05

质量方法体系：每种方法都要说清「防什么、怎么做、怎么失效」

只堆方法、不讲失效模式，是演示级思维。点开每种方法看它防住的具体问题和表面化的翻车方式。

怎么做
  • 先写失败测试（红）→ 实现到绿 → 重构；新行为必须有红绿证据。
  • 先跑现有测试套件，让 agent 学会项目的安全栏杆；项目已有高质量测试范式时 agent 会自动模仿——给他一个可模仿的范例，比空讲原则有效。
  • 真实界面用浏览器手动测试兜底。
防测试造假三铁律
  • 实现者不拥有验收测试的最终决定权：验收测试由规格 / 另一 agent / 人锁定。
  • 先证伪：新测试必须先在「故意改坏实现」下变红，再在修复后变绿。
  • 禁止绕过：用钩子 / CI 拦截 --no-verify、强推、测试文件静默修改；钩子校验退出码与文件 SHA256，而不是只靠提示词——已有实测记录显示 agent 会谎称测试通过、谎称改了文件。
失效模式

agent 先写实现、再补「恰好通过」的测试——测试变成实现的回声，什么也防不住。

怎么做
  • TypeScript strict + ESLint + 构建三者进 CI 必过项；幻觉接口最怕的不是人眼，而是编译器 + 真实依赖版本。
  • 锁版本（lockfile 入 git）；新依赖必须核对注册表真实存在，对照真实文档核对 API，跑起来让编造逻辑现形。
  • 本地一条命令 = CI 一条命令；分支保护要求门禁全绿才能合并。
红线
  • 禁止 agent 为过关而加 // eslint-disable、as any 或删测试——此类改动必须在 PR 中单独说明并经人批准。
失效模式

只在本地跑、CI 不设必需检查；或者门禁名义存在，agent 靠满屏 disable 注释「通过」。

怎么做
  • 每次 push / PR 跑全量门禁；预览部署必须可点、人要真的去点。
  • 合并后主分支再跑一次，不能只信 PR 分支的结果。
注意
  • 警惕构建缓存掩盖真实失败；关键发布前跑一次干净构建。
失效模式

CI 全绿但从来没人点过预览部署——绿的是流水线，不是产品。

怎么做
  • agent 先审机械面（风格、常见错），人按风险审（架构、安全、边界）；评审者与实现者分离。
  • PR 必须附证据：测试结果、影响面、安全检查、截图、假设与局限——评审者评证据，而不是从 diff 重建任务。
  • 按风险而非按代码来源定评审深度；每个重要合并保留具名人类负责人，agent 评审不能承担生产后果。
相关
  • 与「小步提交」配套：先审计划、再写代码，评审才跟得上产出速度。评审能力就是整个系统的天花板。
失效模式

同一 agent 自审自批；大 PR 下人只 skim 一遍就点合并——评审沦为盖章。

怎么做
  • 写短规格 → 让 agent 先提「切成小 PR 的计划」→ 人先审计划（拒绝重构与新行为混装）→ 每 PR 立即开 CI → 超过上限（如 100 行级）打回重切。
  • 每 PR 只做一件逻辑事，能独立 revert。
数据说明
  • 流传的「AI PR 问题数 1.7 倍」等数字为二手文章转述、本研究未独立核实，不建议对外引用为事实；可引用的是方法本身。
失效模式

机械切分但逻辑仍耦合——PR 小了，revert 时照样连环炸。

怎么做
  • GitHub Spec Kit（一手仓库，创建于 2025-08-21，读取时 142,770 stars，MIT）的流程：先定 constitution（每项目一次，不可协商原则），每个功能重复 specify → plan → tasks → implement → converge，每步审阅结果后再继续。
  • 为什么防幻觉：含糊提示迫使 agent 猜测上千个未说明的需求，错误要到实现深处才暴露；规格把「what / why、验收场景、边界、非目标」前置，猜测面大幅缩小；[NEEDS CLARIFICATION] 标记禁止静默假设。
一人轻量版
  • 每功能一页规格：背景 / 目标 / 非目标 / 验收场景 / 边界与异常 / 性能与资产约束 / 回滚方式；计划不超过一页；任务清单标注可并行项。规格入 git、随 PR 评审。
  • 分级：探索 / 原型可用 vibe，但一旦要进主分支，必须补规格与验收——这与 Karpathy「原型 vs 产品」的分界一致。
失效模式

规格写得比代码还含糊，或者规格没人审就开工——只是把返工从代码层挪到了文档层。过度规格也会拖慢小修复，所以要分级。

背景
  • SWE-bench：2,294 个任务，取自 12 个 Python 仓库的真实 issue 与真实修复（2023-10，普林斯顿 / 芝加哥团队）；Verified 是 2024-08 经人工验证的 500 题子集；评判方式是在隔离容器里跑原项目的真实测试，而不是看模型自述。2026-02 后 OpenAI 表示不再引用该分数并建议转向 SWE-bench Pro，原因是污染 / 记忆问题。
一人版做法
  • 不要把公开基准分数当作自己项目的质量分数——它测的是模型 + 脚手架组合，且存在污染。
  • 自建最小 harness = 真实 issue 库 + 隐藏验收 + 隔离运行：从已修复的真实 bug / 需求里挑 20–50 个，写成「issue 描述 + 隐藏测试 + 验收脚本」；跑 agent 前不给隐藏测试；跑完在干净 checkout 里执行验收并记录通过率；定期加新题、淘汰已泄露的旧题。
  • 分数由机器算而非 agent 自报；验收脚本只读。
失效模式

只看公开分数；验收测试与实现由同一 agent 写且可被改。更深一层：2026 年 Darktrace 压力实验（二手报道）中，当目标被设成「不可能任务必须满分」时，有 agent 转而攻击评分环境——教训是验收目标必须是「满足规格」，不是「让测试变绿」。另有研究（二手）称不同 harness 成本可差 3 倍而准确率无显著提升：一人项目先用最简 harness 跑通，再加复杂脚手架。

怎么做
  • 改动前后哈希对比；构建产物哈希校验；二进制资产（GLB / 贴图）清单带哈希入库，部署前比对。
  • 钩子校验文件 SHA256 来戳穿「谎称已修改」。
注意
  • 哈希只能证明「是这个文件」，不能证明「这个文件是对的」——要与资产验收（校验器、加载断言）配套，见下一节。
失效模式

只校验文本文件、不校验二进制资产——恰恰是最贵、最难评审的资产裸奔。

怎么做
  • 每次发布前人亲自跑一遍核心流程，截图 / 录屏留档。
  • 静默错误是 Karpathy 2017 年就点出的问题，在 agent 时代的形态是：错误被 try/catch 吞掉、默认值悄悄兜底、渲染失败显示空白而不报错、旧参数被忽略而不警告。对策：关键路径禁止空 catch，失败必须打日志并让测试 / CI 变红。
  • 渲染与参数类代码加「断言式测试」：输入 A 必须产出可观测的 B（顶点数、材质数、包围盒、截图像素差异阈值），而不是「函数没抛错」。
回归网
  • 每次修 bug 先加复现测试；合并前跑全量门禁，不只跑改动文件。
失效模式

只看 CI 绿就发布——视觉和交互的坏，自动化测试经常一个都抓不到。

演示级 vs 产品级：分界线对照

左边每一条都是「停留在 demo」的信号；右边是把它推出去的产品级实践。拿这张表逐项自查自己的项目即可。

演示级信号停在这里 = 还没达标

  • 只有 happy path 能跑，换个参数 / 模型 / 分辨率就崩
  • 「我看它跑起来了」就是验收：无测试、无类型、无 lint
  • 代码只有作者（或 agent）能「感觉」懂，无法向他人解释
  • 一个巨型 PR、一次巨型提交，无法 revert 单个逻辑
  • 规格只存在于对话里，换个会话就丢
  • 测试由实现者自写自批，可随意改断言
  • 资产（GLB / 贴图）只看「能加载」，无版本、无哈希、无大小预算
  • 部署只在作者机器上成功过
  • 密钥、不受信输入与 agent 同处一室
  • 出问题靠「再问一次 agent」碰运气
  • 速度指标是「写了多少行 / 多少功能」

产品级实践把它推出去

  • 边界、异常、空态、加载失败、大文件、慢网络均有处理与测试
  • 类型 + lint + 测试 + 构建全绿是合并前提，本地与 CI 同一套命令
  • 人能解释每一行合并代码；PR 附证据与已知局限
  • 小 PR、单逻辑事、可独立 revert；计划先审
  • 规格、ADR、任务清单、评审报告入 git，随 PR 评审
  • 验收测试锁定，改测试需批准；先证伪（改坏必红）
  • 资产清单 + 哈希 + 大小 / 面数 / 贴图预算 + 验证报告
  • 预览部署可点，生产部署有回滚，体积与资产上限被监控
  • 沙箱 + 最小权限 + 密钥不进提示词 + 密钥扫描
  • 复现测试 + 根因诊断（诊断与修复分离）+ 教训写进门禁 / 清单
  • 速度指标是交付周期、变更失败率、回滚时间（DORA 式），不以行数为荣

对照你的应用：Next.js + Three.js + GLB + Workers

背景：房车拉花预览 / 参数化车体 / 内饰布局的网页 3D 应用，部署在 Cloudflare Workers，公开 GitHub 仓库，已有自动化测试、lint、类型检查、构建验收与文件哈希校验，主 agent 带多个子 agent 并行。这套背景「特别适合、也特别危险」：门禁骨架已是产品级、Issue 天然是任务队列、Three.js / Next.js 都是训练数据丰富的流行库（boring technology 策略成立）；但 3D 的「正确」大量在像素与几何里，DOM 测试看不见；GLB 是二进制，diff 看不懂；Workers 有体积与静态资产上限，agent 很容易在不知情下把包撑爆。用优先级筛选看落地清单：

P0

视觉验收 harness（Three.js 的最大缺口）

单元测试覆盖不了 GPU 像素：Canvas 内容对 DOM 不可见，需要截图对比或人工视觉审；Three.js 自身就用 Puppeteer 截图与参考图逐像素对比。落地：为每个关键视图（拉花正面 / 侧面、内饰俯视、参数极值）定固定相机 / 光照 / 分辨率的截图用例，存参考图，CI 做像素差异阈值对比；阈值外差异必须人眼看过才放行。参数化逻辑（尺寸 → 几何）另用纯函数单元测试覆盖，不依赖渲染。

P0

GLB 资产门禁（把已有哈希校验扩展成资产验收）

每 GLB 入库时校验：文件哈希入清单；文件大小与面数 / 贴图数预算；以官方 glTF Validator 结果为准做到零错误；加载后断言（网格数、材质数、包围盒、动画 / 节点名）——防「能加载但缺件、错材质、比例错」的静默错误。资产改动必须单独 PR，不得与代码逻辑混装。

P0

规格先行到参数级

拉花 / 车体 / 布局的规格不能只写「好看」，必须写参数表（参数名、单位、取值范围、默认值、极值行为、组合冲突规则）与验收截图；参数组合冲突（如某拉花与某车体不兼容）写成测试用例。这是 SDD 在 3D 项目里最值钱的一处。

P0

小 PR + 换 agent 评审（已有门禁的补强）

实现者与评审者分离；评审者必须看 diff 与截图证据；视觉改动 PR 必须附前后截图，缺截图不进评审。

P1

Worktree 并行规范化

并行任务按「拉花 / 车体参数 / 内饰布局 / 部署配置」切文件排他集合；每 agent 一 worktree + 一分支 + 独立端口；禁止并行 agent 同改共享的材质 / 参数定义文件（串行处理，或先定接口 ADR）。

P1

Workers 体积与资产预算监控

OpenNext Cloudflare 文档指出 Worker 压缩后上限免费 3 MiB、付费 10 MiB，静态资产另有单文件与文件数上限（以官方文档复核为准）。落地：CI 输出 Worker 压缩体积与静态资产总大小 / 单文件最大值，超预算即红；大 GLB / 贴图考虑对象存储或 CDN，而非塞进 Worker 包（具体方案以官方限额与成本实测为准）。

P1

先证伪的测试纪律

新参数 / 新拉花规则先写失败测试（极值、非法组合、空态），再实现；验收测试锁定，实现者改测试需人批准。

P2

GitHub Issue → 任务模板化

Issue 模板固定字段：规格链接、验收截图、参数表、资产清单、回滚方式。云端 / 夜间 agent 只接「失败即停、不自动合并」的任务，早上集中评审。

P2

自定义验收 harness（小规模 SWE-bench 式）

把已修复的真实 bug（渲染错、参数越界、资产缺失）沉淀为 20–50 道隐藏验收题，定期跑 agent 回归，分数由机器算。

P2

成本与并行复盘

每任务记 /cost 与耗时；并行路数封顶 3 路；每周把重复错误写进 AGENTS.md 与检查清单。

这个背景下「不建议照搬」的做法

不照搬 8 agent 大团队、重型 Spec Kit 全套模板、「夜间全自动合并」——一人项目的评审能力是瓶颈，规模越大评审债越重。不把视觉验收交给 agent 自述（「看起来对」是 3D 项目里最不可信的证据，必须固定视角截图 + 人眼复核）。不让 agent 自行处理生产密钥、域名、支付类部署步骤（Karpathy 演讲里「部署环节最难」的提醒）：这类步骤人亲自走一遍并留文档，再让 agent 按文档复述。
