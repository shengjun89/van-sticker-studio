## 2. 建议的分层与状态所有权

```text
React 界面：左侧折叠面板 / 无限画布 / 卡片 / 右侧 AI Chat
        │ 用户意图、命令与查询
        ▼
应用层：编辑命令、历史恢复、模板应用、提交出图、权限编排
        │ 事务化调用                    │ 生成提交
        ▼                               ▼
领域层：基线 / 布局 / 配件 / 外观 / 版本    服务层：身份、权益、任务、成本记录
        │                               │
        ▼                               ▼
适配层：Three.js / 本地保存 / 导出         持久存储 / 队列 / AI 供应商 / 云资产
```

以上模块划分为建议，不要求每层独立部署，也不要求引入微服务。

| 层或模块 | 建议职责 | 不应承担 |
| --- | --- | --- |
| Canvas UI | 卡片坐标、缩放平移、选择、browse/edit 模式与输入焦点 | 改写模型几何、判定会员权益、结算生成成本 |
| Model Editor UI | 左侧车型/外观/配件折叠面板、合法操作入口、ghost 反馈 | 绕过领域校验直接改 Three.js 对象后即认定保存完成 |
| AI Chat UI | 收集意图、展示方案与确认、关联任务及结果 | 将自然语言内容直接当可执行几何命令或付费授权 |
| Application Commands | 校验前置条件、组织原子变更、撤销/恢复、持久化调用 | 在任意页面组件中散落清空布局与变更基线的逻辑 |
| Domain Core | 纯数据与几何规则、版本兼容、约束校验、哈希 | 依赖 DOM、React 生命周期或某个 AI SDK |
| Scene Adapter | 从领域状态生成低模场景、拾取、预览、固定机位渲染 | 把 `Object3D` 当唯一业务数据源 |
| Persistence | 游客本地真实保存、登录后云文档及不可变版本存储 | 将请求完成或 toast 当保存成功 |
| Generation Orchestrator | 四图任务、逐项状态、恢复、重试与幂等 | 在浏览器断开时默认判定上游已取消或未计费 |
| Policy / Entitlements | 分别判断身份、资源权限、功能权益和可用额度 | 以一个 `isMember` 布尔值代表全部授权 |
| Export Adapter | 对象层级、单位、变换和导出清单 | 把低模网格包装成已验证参数化 CAD |

### 2.1 输入路由与视角恢复

确定的交互规则：browse 模式下双击模型卡进入 edit；Esc 退出并恢复进入前的 2D canvas viewport。3D 相机是否同时恢复尚未确认。建议将两类状态分开管理：

- `CanvasViewport`：无限 2D 画布的平移、缩放。
- `ModelCameraState`：某张卡的 3D 相机、观察目标、投影参数。

进入 edit 时保存一份临时 `EntryCanvasViewport`，退出时恢复原 2D 画布平移与缩放；它不应被生成结果到达或后台事件覆盖。`ModelCameraState` 的退出行为不得在实现中默认当作已确认规则。具体动画、保存周期与跨刷新是否恢复编辑态，仍待交互细化。

建议由输入路由器保证同一手势只归一个接收方：browse 的卡片拖动与画布平移、edit 的 OrbitControls 与配件拖放、Chat 文本输入分别处理。输入框中的 Esc、组合输入及弹层关闭优先级应在交互规范中明确，不应靠全局键盘监听偶然决定。

### 2.2 多卡片渲染预算

无限画布不意味着无限个持续运行的 WebGL 上下文。建议 browse 中非活动模型卡使用缓存预览或受预算约束的低频渲染，edit 卡获得实时交互资源；复用渲染器还是池化实例需通过真实设备测试选型。缓存是展示层优化，不改变每张卡的真实模型快照。不可用“卡片是一张图”替代要求中的可编辑实时低模。

## 3. 建议领域实体

以下为逻辑模型，字段名和存储形态均为建议；不是已存在的 TypeScript 接口或数据库表。

| 实体 | 建议关键数据 | 主要约束 |
| --- | --- | --- |
| `Project` | ID、所有者/本地归属、标题、schemaVersion、创建与更新时间 | 游客可拥有本地项目；登录不自动等于有所有云端资源权限 |
| `CanvasDocument` | Project ID、卡片集合、2D 卡片位置和尺寸、画布视角 | 卡片排版与物理空间坐标独立 |
| `ModelCard` | ID、工作副本引用、标题、画布位置、当前展示版本 | 只有用户显式“复制/重新初始化”等新卡动作才增加模型卡 |
| `ModelWorkingCopy` | ID、revision、完整当前状态、最新保存状态 | 可持续编辑；不是提交给 AI 后仍可被修改的版本对象 |
| `VehicleBaseline` | 车型、可选的公告记录 ID/版本、资产修订、固定锚点、基线几何、允许的外壳参数 | 真实车型轴距、轮位和驾驶室锁定；入库完备性和参数值都不是实车匹配或制造证明 |
| `Layout` | ID/revision、空间几何依赖、配件实例集合、模板来源 | 存在布局时锁定空间几何；不能因应用模板而自动新建模型卡 |
| `AccessoryDefinition` | 类型、默认/允许尺寸、资产版本、容纳区域、碰撞体、材质槽 | 库定义与实例分开；不为了塞入空间自动缩小产品 |
| `AccessoryInstance` | 稳定 ID、定义版本、尺寸、局部变换、parent ID、材质覆盖 | 父子容纳不等于免除碰撞；设备可取出、替换、独立导出 |
| `AppearanceState` | paint/wrap 预设 ID、材质与配色覆盖、必要的图案引用 | 8 套预枚举方案即时本地预览，不调用 AI |
| `UsageContext` | 可选最高身高、人数、场景 | 缺省时用车型 default；不从空值推断用户画像 |
| `LayoutTemplate` | ID/version、适用车型/空间约束、候选布局、匹配元数据 | 匹配是建议，不等于人体工学或实车适配通过 |
| `ModelSnapshot` | schemaVersion、基线、布局、配件、外观及资产依赖的完整值 | 单卡恢复完整 snapshot；基线与布局必须一起恢复 |
| `ModelVersion` | ID、不可变 snapshot、来源 working revision、哈希、创建原因 | submit 时冻结；已提交版本永不追随之后的编辑 |
| `StylePreset` | ID/version、允许的材质配色光照装饰参数 | P0 由 preset 驱动；不得包含变更空间布局的授权 |
| `CameraPresetSet` | ID/version、4 个固定机位定义 | 1 个 exterior + 3 个 interior；具体镜头位姿待确认 |
| `GenerationTask` | ID、owner、ModelVersion ID、style/camera 版本、4 个 item、执行摘要 | 生命周期独立于当前页面、选择卡片和浏览器连接 |
| `GenerationItem` | ID、固定机位、attempt、服务状态、质量状态、产物引用 | 逐图真实状态，不用总体完成替代单项成功 |
| `ImageResultCard` | ID、task/version 引用、画布位置、4 个 slot 及其 item 引用、展示状态 | 一次提交创建一张四图分组结果卡，4 个 slot 分别展示四个 item；结果不覆盖当前模型或抢焦点 |
| `AssetRecord` | ID、存储位置、类型、校验和、来源版本、访问控制 | 对象存储 URL 不是永久访问权限 |
| `CostQuote / Settlement` | 报价 ID/有效期/范围、确认凭据、结算引用 | 金额、单位、预占/扣减及失败计费细则待定，不伪装真实支付 |
| `Entitlement / QuotaDecision` | 功能类型、资源范围、额度、判定依据 | 图片、模型导出、高级配件与额度分别控制 |

首批 10 类配件为：床架、卡座、餐桌、厨柜、储物柜、吊柜、冰箱、空调、马桶、淋浴间。建议以稳定类型 ID 配中文标签，而不是把名称写进场景节点后反向猜测业务类型。首批资产是否为自建通用低模、厂家参考或具体商品，应在资产登记中标清，不能混称原厂精模。

### 3.1 父子关系、容纳与碰撞分别建模

建议区分三件事：

1. **变换层级**：`parentInstanceId` 决定设备跟随哪个柜体运动，保证导出层级可追踪。
2. **容纳关系**：`ContainmentSlot` 描述柜体内部允许放置的体积、接口方向及适配范围。
3. **碰撞规则**：独立的碰撞体及规则集判断实体相交、越界或保留净空。合法容纳只允许设备位于柜体空腔，不允许它穿过柜板。

拖放时先计算候选放置，再运行边界、容纳、碰撞与 snap 校验。合法时显示可提交 ghost；非法时说明原因并保持原实例不变。合法 snap 可以调整允许的放置位置/朝向，但不得偷偷缩放尺寸。更细的 snap 优先级、碰撞精度、净空数值和复杂形状算法均需选型，不在本文虚构毫米阈值。

设备取出时建议执行保留世界变换的 reparent，清除旧容纳绑定后重新校验；替换设备须用新定义的真实/候选尺寸再判断，不能沿用旧设备包络而只换名称。父子图必须无环，删除父对象对子设备的行为尚需明确产品规则，不由底层递归删除默认决定。

## 4. 基线、布局、版本与依赖

### 4.1 基线的范围

确定规则：真实车型 baseline 锁定轴距、轮位、驾驶室；外壳可做 rounded/rugged 方向的参数调整。建议将固定锚点与可调参数分开存储：

- 固定部分：车型/资产身份、轮轴与轮位锚点、驾驶室不可变区域、已登记开口与连接关系。
- 可调部分：外壳风格及经过允许范围定义的 shape parameters。
- 来源说明：模型资产修订、尺寸来源、未实测项、与实车/工程文件的同步边界。

rounded/rugged 是设计表达能力，不意味着任意参数组合都可制造、可上牌或能与当前家具安装。参数范围、拓扑适用区、开口处理及真实基线数据来源需要专项验证，不能通过滑块能拖动就认定有效。

### 4.2 有布局时的几何锁

确定规则：有 layout 时锁定空间几何；用户必须明确确认清空 layout 后才能改基线，清空前保存完整 snapshot，现有配色保留。外观材质、配色及不改变空间的 8 套 paint/wrap 可以继续切换。

建议将变更基线实现成单一应用命令，而不是多个 UI 回调：

1. 收到几何变更意图，检查最新 working revision 与 layout 存在性。
2. 有 layout 时展示清空影响，等待明确确认；确认对象绑定该卡片及当时 revision，避免对错卡或旧状态生效。
3. 确认后，在一次原子变更中保存可恢复的完整旧 snapshot、清空当前 layout、保留现有配色，再应用基线变更。
4. 任一步失败则保持原状态。撤销/恢复时 baseline、layout、配件与外观按同一 snapshot 回来，不拼接成混版。

保存清空前的完整 snapshot 和保留现有配色是确定规则；上述原子操作、版本校验与确认弹窗文案是技术/交互细化。不得设计为“改了基线后发现放不下再自动清布局”。

### 4.3 工作副本、历史快照与提交版本

建议明确三个不同概念：

- `workingRevision`：当前可变工作副本的乐观并发序号，用于保存冲突与命令前置条件。
- `historySnapshot`：同卡的完整历史状态，用于恢复，不新增 `ModelCard`。
- `submittedVersion`：submit 时冻结的不可变 `ModelVersion`，任务与结果只引用它。

模板替换、改变模板匹配条件、调配件、切换风格、生成图片、恢复历史都不自动分叉模型卡。只有用户显式执行新卡动作时才创建新 `ModelCard`，并清楚表达是复制还是重新初始化。

建议 snapshot 包含基线、布局、所有配件实例及父子图、外观、资产定义版本、必要的空间参数与 schemaVersion。活动选择、高亮、拖拽中的 ghost、临时 loading、当前聊天输入等不是完整模型 snapshot 的组成部分。画布排版可随 CanvasDocument 独立保存。

### 4.4 建议的依赖指纹

```text
资产修订 + 固定基线 + shape parameters
                    └─ 空间几何指纹
                          └─ layout / 配件 / 父子图 / 约束版本
                                  └─ 几何快照指纹
外观 + style preset + 固定机位 + 生成配置 ─┴─ 渲染输入指纹
```

建议将依赖的内容版本/哈希记录进不可变版本，避免“今天同一个预设 ID 已经换了内容”导致重放不一致。正常 orbit 观察不应改变固定机位出图输入；若设计内容变化导致当前状态与来源快照不一致，旧结果标记 stale/来源旧版本，保留原图与引用，不覆盖新设计。具体哈希规范和 stale 展示逻辑仍待实现评审。

资产升级不得自动迁移已提交版本或重写历史图来源。建议用 schema migration 与 asset compatibility 检查显式处理：可恢复则迁移工作副本并留迁移记录；不兼容则提示，禁止靠缺失节点默认值生成貌似正常的场景。

## 5. 坐标、单位与几何归一策略（建议，未确认）

建议建立独立于 Three.js 的物理坐标约定：

| 项目 | 建议约定 | 理由与注意事项 |
| --- | --- | --- |
| 领域长度单位 | mm，字段名或 schema 明确单位 | 与尺寸面板、模型测量及后续工程交接对齐，避免 1000 倍误差 |
| 领域坐标轴 | 右手系：X 向车头，Y 向车辆左侧，Z 向上 | 三个方向有明确车辆语义；最终需与资产实测核对 |
| 原点 | 候选为固定后轴中心在基准地面的投影点 | 原点不能跟外壳长度或布局变化漂移；此选法尚未确认 |
| Three.js 适配 | mm→m；结合现有车头朝 -X、Y-up 约定，候选映射 `(X,Y,Z) → (-X,Z,Y)`，再加经过登记的资产变换 | 这是对上述候选领域坐标的适配建议，必须按真实资产核对；不能直接改历史资产坐标或省略正负方向转换 |
| 对象变换 | 明确 local/world；领域尺寸与位姿分开，归一后避免残留非均匀 scale | 替换、父子解绑、碰撞和导出使用同一变换来源 |
| 旋转 | 候选四元数作为持久值，界面按需展示角度 | 避免欧拉角顺序被不同工具各自解释；需定义规范化和精度 |
| 2D 卡片坐标 | canvas 逻辑像素/独立画布单位 | 与物理 mm 无换算关系，不因卡片缩放改变车或家具尺寸 |
| 数值精度 | 运算可保留浮点；显示、吸附、比较容差分别定义 | 不能把显示取整后的数值当精确碰撞依据；具体容差待选型 |

建议在资产导入时记录原始单位、轴向、原点、归一矩阵、轴距锚点及包围盒。禁止按每个导入资产的包围盒“自动铺满空间”，因为这会破坏真实比例和配件尺寸。

必须验证同一已知长度在领域数据、Three.js 预览、导出文件与目标软件中的读回一致；同时验证左右不镜像、轴距和轮位不漂移、父子解绑前后世界变换一致。当前历史 GLB 是否完全满足新约定应先审计，不能在文档中假设。

## 6. 持久生成任务与恢复（建议技术方案）

确定的 P0 行为：选择 preset 风格本身不提交生成。生成按钮必须显示本次张数（1 张 exterior + 3 张 interior，共 4 张）、预计消耗与剩余额度，由用户主动点击后才提交。调用真实 AI 服务，mock 不能用于正式验收。submit 冻结不可变版本，后台允许继续编辑。一次提交创建一张 `ImageResultCard` 四图分组结果卡，其中 4 个 slot 分别展示四个 item 的真实状态；结果到达不自动选卡、不滚动画布、不改变焦点、不替换当前模型。

张数、预计消耗、剩余额度的事前展示与用户主动点击是确定要求，不属于可省略或待定的首次确认流程。登录、权益与额度检查也不能省略。`CostQuote` 的有效期、报价单位和额度预占/结算细节仍待选型；不能把选择预设解释成付费或消耗额度的授权。

### 6.1 建议提交链路

1. 选择 preset 仅更新风格候选，不提交生成；采集待提交的完整 snapshot，并固定 style、四机位及资产版本。
2. 服务端分别校验身份、项目/版本访问权、图像功能权益、额度及并发限制；准备与待提交输入绑定的 `CostQuote`。按钮展示本次 4 张、预计消耗及剩余额度，不能在缺少这些信息时直接消耗额度。
3. 用户主动点击后才提交；校验报价与候选 revision 仍匹配，冻结不可变 `ModelVersion`，并关联报价与本次用户确认。输入变化时重新校验，不能沿用针对旧输入的授权。报价有效期、额度预占及具体持久化顺序待选型，不改变上述确定的用户确认要求。
4. 以客户端提交幂等键创建一个 `GenerationTask` 和四个稳定 item，并为本次提交创建一张含 4 个 slot 的 `ImageResultCard`；返回 task ID。
5. 后台逐项准备固定机位参考、调用真实服务、校验并保存产物、更新状态与结算记录。
6. 前端按 task ID 订阅或轮询，更新原分组结果卡内对应的 4 个 slot，不新增四张独立结果卡。连接方式是实现选择，断开并不等于任务取消。

建议使用当前 Worker 作为鉴权与编排入口；持久数据库、对象存储、后台队列/工作流可以评估 D1、R2 及 Cloudflare 的相关能力，也可选其他后端。不在未验证容量、时限、供应商调用和恢复方式前宣布选型完成。不能仅在一个长 HTTP 请求内执行全部工作并称为可恢复后台任务。

### 6.2 逐项状态和整体状态

建议把“服务执行”和“质量验收”分开，避免服务返回图片就被误报为布局保真成功：

| 维度 | 建议状态 | 含义 |
| --- | --- | --- |
| item 执行状态 | `queued → preparing → running → succeeded / failed` | 真实的排队、参考准备、供应商执行及产物存储情况 |
| item 质量状态 | `not_checked → checking → accepted / rejected / needs_review` | 是否满足当前版本和固定机位的空间保真要求；具体检测方式需验证 |
| task 汇总状态 | `queued / running / succeeded / partial_failed / failed` | 四项真实执行状态的派生摘要，不替代每张图的质量状态 |
| 恢复异常标志 | `status_unknown / reconciliation_required` 等候选 | 本地或上游证据不充分时显式标记待核，不能伪造失败或完成 |

执行成功且保存完毕的图片，也可能质量待核或被拒绝；界面应可看图但明确状态，不能用模糊的“已完成”掩盖空间错误。是否把质量不合格归入用户可重试的“失败项”，及其成本承担，仍须产品与供应商能力验证后确定。

上述状态名是建议。取消能否中止上游、取消后的已生成图片如何处理、退款条件及模型卡删除后任务/结果如何处理均尚未确认，不在此写成固定终态或业务承诺。设计时可预留独立取消请求/上游确认字段，但不能把浏览器 AbortController 当作已退款的证据。

### 6.3 幂等、断线与刷新恢复

- 客户端生成一次提交幂等键并重用它重试网络请求；服务端按账号与操作范围去重，同键同输入返回同 task，不同输入拒绝混用。
- 每个 item、attempt、供应商请求及产物都有独立 ID；任务事件建议带单调序号，重连可从快照加增量恢复，旧事件不得回退新状态。
- 页面刷新后从已保存的 task ID 读真实状态，并恢复到原分组结果卡的 4 个 slot，而不是重新调用生成或新增结果卡。游客本地的卡片数据不能被当成有权访问他人任务的凭据。
- 后台执行采用可重放步骤、明确租约/超时和持久检查点，避免工作进程重启后丢任务；具体机制待后端选型。
- 上游超时不一定代表没有生成或没有计费。先按上游请求 ID 查证；若供应商不支持状态查询/幂等，应记录不确定状态并制定人工或保守恢复策略，不能自动重复扣费生成。
- 不采用前端倒计时推算成功。已完成的图片必须有真实产物记录与可访问内容，失败须保存可展示原因及内部追踪信息。

### 6.4 partial retry 与成本边界

确定规则：只重试失败项，且重试成本必须由用户确认；不能再次生成已经成功的机位来凑一组，也不能默认把整组重新收费。

建议重试仍关联原始不可变版本，创建失败 item 的新 attempt，保留旧错误和成本记录，更新原分组结果卡对应的失败 slot；不创建新模型卡或新的分组结果卡。用户若想对当前已修改模型出图，那是一次新的版本提交，不是旧任务重试。

新报价须绑定失败 item 集合、版本、风格和配置；重试按钮同样展示本次失败项张数、预计消耗及剩余额度，等待用户主动点击确认后才执行。报价应有明确授权范围，有效期的具体规则待选型。额度检查与消耗必须能在并发下保持一致；预占、实扣、失败结算、赠送额度及账单单位的细节均待定。产品不包含真实支付流程，不应以假扣款、假会员购买或无来源余额完成演示验收。

## 7. AI 不得改变空间：控制层与验收难点

确定边界：AI 只改变材质、配色、光照和装饰，不得改变车型、壳体、窗门、布局、家具尺寸位置或相互关系。这个边界不能单靠 prompt 保证；冻结的数据没有变化，也不能证明 AI 输出的像素没有扩舱、移窗或增删家具。

### 7.1 建议的多层控制

1. **输入白名单**：Chat/风格预设只能提交允许的视觉参数；不得透传任意几何 patch、场景脚本、文件路径或供应商系统提示。
2. **不可变参考**：每个 item 都由同一 `ModelVersion` 的固定机位生成真实低模参考，登记相机矩阵、几何哈希与参考图校验和。
3. **条件约束候选**：评估图像编辑、深度/边缘/法线/分区遮罩等条件输入和可控材质重绘；供应商是否支持、约束强度与效果必须实测，不以概念名词当可用能力。
4. **输出核验**：比较窗门数量位置、主要边界、家具身份及相邻/遮挡关系；结合自动检查与人工同版核图。检测模型与阈值待验证，不在未测前宣称能可靠自动识别一切空间错误。
5. **拒绝与降级**：无法达到空间保真就显示不合格/待核及原因，保留真实低模视图作为事实参考，不用 mock、另一版模型或空间错误 AI 图代替合格成果。

装饰允许范围也应约束：不能借“装饰”增加占地家具、封窗、扩大淋浴间、遮掉通道或把需安装的设备画进不存在的空腔。生成的软装细节如果未建入模型，只能作为视觉参考，不能进入配件清单、尺寸或导出几何。

### 7.2 必须先做的真实能力验证

建议用包含狭窄通道、相邻柜体、窗门遮挡和设备容纳关系的冻结测试集进行真实服务试验，检查四个固定机位，而不是只选一张最好看的外观图。至少记录：输入版本、参考图、供应商配置、真实耗时/错误/成本证据、四张原始结果、逐项空间问题及最终判定。

验收应区分：

- **领域数据正确**：基线锚点、配件尺寸和布局未被改写。
- **实时低模正确**：同版显示、碰撞与尺寸读回满足当前定义的编辑规则。
- **AI 图像保真**：画面实际没有改变空间关系，四图没有互相矛盾。
- **工程可用**：实车复尺、安装净空、承载、热管理、法规与制造验证。前三项通过不自动获得第四项。

若供应商无法在真实测试中达到要求，须回到能力边界/供应商/生成方法评审，不能把要求改成“prompt 已写禁止变形”就宣布通过。P0 的真实 AI 依赖是正式验收门槛，不是待日后替换的装饰接口。

## 8. 本地保存、身份、权益与安全

### 8.1 游客真实本地保存

确定规则：游客可以真实本地保存；出图、云保存、会员下载需要登录。建议采用 IndexedDB 保存 CanvasDocument、完整工作副本和必要的本地引用，保存完成需读回验证与明确失败提示。具体存储实现未选型。

本地持久化受浏览器清理、空间额度、隐私模式和站点数据策略影响，不能宣传成不会丢失的永久云备份。应能区分未保存、保存中、已本地保存及保存失败；失败时保留编辑内存并提供可恢复路径，不能只更新“已保存”文案。

登录后是否迁移本地项目、与云端同名项目如何合并、冲突选择与额度如何处理尚需确认。建议至少不在登录回调里静默覆盖任一侧，迁移应保留来源与恢复记录。

### 8.2 四类判定不能混成会员开关

| 判定 | 回答的问题 | 建议执行位置 |
| --- | --- | --- |
| Authentication | 当前是谁，是否已登录？ | 身份服务及服务端 API |
| Resource authorization | 是否有权读写这个项目、版本、任务、图像？ | 每个资源读写入口 |
| Entitlement | 是否拥有模型导出、高级配件、图片下载等指定功能权益？ | 服务端策略层，前端仅做可理解提示 |
| Quota / cost authorization | 这次操作额度是否足够，是否已确认本次成本？ | 提交与重试的原子检查/记录 |

登录不是会员、会员不是资源所有者、有下载权益不意味着有生成额度。模型 export、高级配件、图片权益与生成额度应使用独立 capability，具体套餐映射待定。没有真实支付需求时，不实现会被误认为已购买或已实际支付的流程。

### 8.3 建议的安全控制

- AI 密钥和对象存储凭据只在服务端，前端状态接口仅暴露必要能力状态；当前同源检查不能替代身份、资源授权、限流与滥用防护。
- 对项目、snapshot、模板、配件参数、父子图和 Chat 派生命令进行服务端 schema 与范围校验；拒绝循环层级、非法数值、超大对象及越权资产引用。
- 任务与图像 API 检查 owner/授权，不靠难猜 ID；下载链接按权限生成并控制有效期，不能把公开 URL 当会员控制。
- 用户文本、Chat 内容、模板说明和图片元数据都是不可信输入；不得据此执行脚本、下载任意 URL 或改变成本确认范围。
- 避免任意外链抓取导致 SSRF；上传/生成产物限制类型、尺寸与大小，按实际媒体内容校验。具体限制数值需测试后确定。
- 成本、额度与幂等记录支持审计；日志隐藏密钥、签名 URL 和不必要的个人信息。公开错误可解释，内部错误保留 request/task/item 追踪 ID。
- 本地内容上云、AI 服务处理、保留期限与删除策略需要清晰告知；不得在删除模型卡语义未定时自行承诺级联删图、取消任务或退款。

## 9. 低模导出边界（格式待选型）

确定目标是导出便于 Blender / FreeCAD 继续处理的独立对象与层级，不承诺原生参数化 CAD、完整制造曲面或 STEP 可用性。

建议导出以不可变 `ModelVersion` 或明确冻结的当前 snapshot 为来源，包含：稳定对象 ID、中文名称、对象类别、父子层级、局部/世界变换、单位、尺寸、材质槽、基线及资产版本、来源与未验证说明。柜体里的设备仍是独立对象，不合并成一个不可拆网格；辅助碰撞体与 ghost 不混入正式对象。

候选方案可评估“场景网格格式 + 结构化 manifest”，或分别提供适合不同目标软件的网格与层级伴随文件。GLB、OBJ、STL 等各有层级/材质/单位能力差异，不能只选扩展名就断言双工具兼容；最终格式必须在约定版本的 Blender 与 FreeCAD 中实际导入、读回并核对。

验证至少覆盖：对象可独立选择、层级无丢失/循环、毫米尺寸正确、轴向不镜像、设备取出后仍保持变换、隐藏/辅助对象处理明确。若 FreeCAD 导入后是网格参考，应直说网格，不把它称作可编辑 PartDesign 实体。网格转 STEP、自动重建特征、参数化装配与工程图生成均不因本导出自动获得，也不属于当前承诺。

## 10. 分批实施的模块边界（建议，不替代排期）

建议按可验证边界拆分，实现优先级与正式里程碑以 [DELIVERY_PLAN.md](DELIVERY_PLAN.md) 为准；以下顺序不是对产品规则的删减。

| 建议批次 | 模块产物 | 进入下一批的证据 |
| --- | --- | --- |
| A：领域与保存基础 | schema、基线/布局/配件数据、命令、完整 snapshot、版本、单位适配、本地真实保存 | 固定锚点、几何锁、清空确认、原子恢复、比例与读回测试通过 |
| B：可编辑画布与模型 | CanvasDocument、modelCard、browse/edit 输入路由、原 2D canvas viewport 恢复、左侧三类面板、10 类配件、snap/ghost/容纳/碰撞、8 套外观 | 真实交互验证；未授权的新卡不出现；设备可取出替换，非法放置不偷偷缩放 |
